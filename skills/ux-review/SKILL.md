# UX Critic

Выполни независимое ревью в своей области и самостоятельно проверь существенные выводы в браузере через **Playwright**. Проверяй собственные гипотезы о дефектах; принятый продукт не исправляй и не передизайнивай. Скилл работает самостоятельно по текущей задаче или как навык назначенного субагента.

Прочитай `references/artifact-contract.md`: применяй единые правила источников, ID, статусов документа, решения, гейта и отдельных проверок, а также выбора папки, сохранения и полного дублирования результата в чате. Это правила формата, а не зависимость от других навыков.

## Вход и обязательные ресурсы

- Прочитай `references/review-protocol.md` и `references/playwright-review.md`: независимость, tool setup, безопасная изоляция, реальные actions/assertions и supplemental evidence.
- Используй `assets/review-template.md`; профильные справочники читать при подготовке метода: `references/cognitive-walkthrough.md`, `references/nielsen-evaluation.md`.
- Для local Playwright доступны `scripts/browser-review.cjs` и адаптируемый `assets/browser-review.example.cjs`. Готовый project setup/MCP использовать при наличии; прототип и предыдущие артефакты не обязаны быть созданы другим скиллом.
- При orchestration сверить run_id/revision/capture_sha256/read-set. При standalone получить task/URL/контракт из текущего запроса; отсутствие документа само по себе не дефект. Без interactive доступа оценить предоставленное с ограниченным scope и NOT_CHECKED, не имитируя browser прогон.

## 1. Определи контракт и покрытие

Прочитай назначенные TASK/requirements, решение/сценарии, flow/ui и evidence. Готовые документы необязательны: при standalone сформулируй минимальный review brief из запроса, явно указав источник и неизвестное. Не выводи обязательный контракт только из того, что уже реализовано.

Установи целевую роль, её подготовку, primary goal, entry/success conditions, P0 alternative/recovery paths, платформы и рискованные условия. Изменение scope или unknown semantics оставь вопросом; не придумывай новую механику. Выполни матрицу «сценарий → significant steps → states → проверить через browser/provided evidence».

## 2. Пройди Cognitive Walkthrough в браузере

Открой отдельный Playwright context/fixture и **сам пройди основной путь** обычными действиями. Затем пройди meaningful P0 alternate/error/recovery. Подробности — `references/cognitive-walkthrough.md`.

На каждом значимом шаге запиши:

- Goal — понятен ли ожидаемый промежуточный результат;
- Discoverability — видит ли целевой пользователь доступное действие;
- Mapping — связывает ли видимый control с нужным результатом;
- Feedback — понимает ли фактический outcome и следующий шаг.

Для каждого значения yes/risk/no/NOT_CHECKED укажи конкретное наблюдение. Знание DOM/test-id не приписывай человеку. Direct deep link полезен для осмотра state, но не заменяет прохождение user path. Это экспертный walkthrough, не реальное исследование пользователей.

## 3. Выполни Nielsen Heuristic Evaluation

Обязательно прочитай `references/nielsen-evaluation.md`. Рассмотри **все десять линз**, задавая профильные вопросы и выполняя применимые Playwright probes. Не ограничивайся упоминанием названий и не находи по одному дефекту на каждую эвристику.

| ID | Что оценивать | Пример браузерной проверки |
|---|---|---|
| N1 | Понимание текущего состояния и результата | Click → processing → success/error/partial, counts и доступность next action |
| N2 | Язык/модель задачи пользователя | Сопоставить реальную терминологию input, confirmation и outcome с glossary |
| N3 | Контроль и выход без неожиданных потерь | Back/Cancel/Escape, состояние введённого, допустимый recovery |
| N4 | Последовательность смысла controls/states | Сравнить одинаковое действие в двух contexts, реально выполнить его |
| N5 | Предотвращение предсказуемой ошибки | Invalid data/eligibility/double-submit на безопасной fixture |
| N6 | Доступность нужного контекста в момент выбора | Selection → configuration → confirmation без скрытой необходимости помнить |
| N7 | Эффективность заявленной частой задачи | Повторный/keyboard/bulk путь по scope; фактические действия и потери контекста |
| N8 | Приоритет существенной информации | Data-rich/narrow/error states, видимость главного действия и итога |
| N9 | Понимание ошибки и реальное восстановление | Error/partial → correction/retry → результат и сохранность успешного |
| N10 | Помощь там, где она нужна | Найти/открыть подсказку и вернуться к задаче, проверить relevant input alternatives |

В отчёте и heuristic_coverage укажи по каждой N1–N10 scope, checked/issue/not_applicable/not_checked, check IDs/evidence, findings или причину. N/A означает неприменимость к задаче; недоступный screen/время/отсутствующий браузер означает NOT_CHECKED. Для общей линзы можно оценить весь flow вместо бессмысленной проверки каждой строки таблицы.

## 4. Проверь product/flow consistency

Сопоставь обязательные действия, роли/guards, важные состояния, данные и outcomes с источниками. Проверь, действительно ли основной CTA завершает задачу; не потеряны ли recovery и принятое поведение при ошибке/partial. Не объявляй server permissions/persistence доказанными через UI.

При наблюдении существенного препятствия основной работе сначала исследуй его и последствия. Не трать весь scope на мелкие эстетические предпочтения, пока неизвестен результат задачи. Отсутствие отдельного необязательного документа не является дефектом продукта.

## 5. Самостоятельно проверь предполагаемые дефекты

Сформулируй гипотезу «в условии X действие Y приводит к Z, противореча источнику». Через Playwright воспроизведи её, запиши expected/actual и сохранность данных, затем targeted повтори с clean fixture и проверь альтернативное объяснение.

Не считай timeout неверного selector подтверждением плохой discoverability. Не используй force clicks/internal handler для доказательства пользовательского пути. Если подозрение опроверглось, не создавай finding; если стало intermittent, запиши условия и неопределённость.

## 6. Собери единый UX-вывод

Объедини walkthrough, Nielsen и consistency без дублей одного нарушения. Номер heuristic не определяет severity. Вывод об эффекте, не измеренном пользователями, обозначай экспертным риском; числа/цитаты не выдумывай.

What works well укажи по observed action/state и источнику. Отдельно запиши непроверенные состояния, открытые продуктовые вопросы и actual browser coverage. Хорошо выполненная часть не скрывает missing P0.

## Перед завершением

Пройди `references/review-ready-checklist.md`, включая live browser checks, профильное покрытие и limits. Сверь Markdown, review-data, actual evidence paths/hashes и отсутствие source edits. Новое evidence сохраняется отдельно от immutable capture. PASS относится к полноте заявленного ревью; полный interaction scope без фактических checks не получает complete.

## Артефакт

Выбери и при необходимости создай `<task-dir>` по `references/artifact-contract.md`. Сохрани основной документ в `<task-dir>/reviews/ux.md` при самостоятельном запуске; в оркестрации используй назначенный путь `<task-dir>/reviews/<run-id>/ux.md`. После сохранения продублируй полный Markdown в пользовательском чате вместе с кратким выводом и ссылками на файлы; при работе через субагента доставку выполняет основная сессия. При недоступной записи выдай полный текст и явно сообщи, что файл не сохранён.

Сформируй и отправь **один `ux.md` в формате Markdown**: scope/revision/read-set, профильное coverage, самостоятельные Playwright checks с expected/actual, What works well, findings или явное отсутствие замечаний в проверенной области, limitations и gate, один review-data.

Findings начинаются с `UX-`. Собственные scripts/screenshots/traces/logs — attachments в `evidence/ux/<attempt>/` рядом с отчётом; включи реальные пути/sha256 в evidence_files и deliver вместе. Не меняй чужие отчёты, canonical inputs, код/тесты и source capture.
