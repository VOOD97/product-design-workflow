# Контракт артефактов и статусов

## Самостоятельность и источники

Работай по текущему запросу и доступным материалам. Ни один документ из таблицы не является обязательным предварительным входом. Если источника нет, опиши минимальный необходимый контракт внутри своего основного результата, явно отделив факты, решения и неизвестное. Не создавай документы других процессов для заполнения цепочки.

| Данные | Основной источник, если предоставлен |
| --- | --- |
| Требования и проблема | requirements.md |
| Наблюдения об аналогах | competitive-research.md; Research Stand — при выбранном document+stand |
| Механизм, правила, состояния и сценарии | solution.md, включая раздел «Сценарии» |
| Пути пользователя | flow.md; локальное представление или FigJam — только по выбранному формату, та же модель |
| Экраны, состояния и взаимодействия | ui-spec.md; Design Stand — представление того же контракта |
| Матрица тестов и журнал реализации | prototype-build.md; нейтральный блок prototype-test-contract отделён от авторских notes |
| Собранные свидетельства | manifest.md и связанные raw evidence |

Предоставленные отдельно старые/внешние документы допустимы как источники с версией, происхождением, полномочностью и областью. Их имена не дают приоритет. При конфликте выясни действующее решение по фактам и полномочиям; если это невозможно, сохрани вопрос/blocker. Не создавай второй основной источник тех же данных и не обновляй чужие документы молча.

JSON для инструментов, код, изображения, traces и стенды — технические материалы или представления, а не дополнительные обязательные аналитические Markdown-отчёты. Производный файл сохраняет происхождение/ревизию и проверяется против источника. Независимым reviewers передавай нейтральный контракт и наблюдения; авторские build-notes/самооценку не передавай.

## Сохранение и доставка результата

Применяй эти правила при любом запуске, в том числе самостоятельном: наличие `requirements.md` и запуск других скиллов для сохранения не нужны.

1. Выбери папку задачи (`<task-dir>`): явно указанная пользователем папка → уже установленная папка этой же задачи → `work/<task-slug>/` относительно корня рабочего проекта (без проекта — текущей рабочей папки). Используй устойчивое короткое имя задачи; не выбирай чужую папку по времени изменения. Создай отсутствующие каталоги. При продолжении используй ту же папку. Указанный точный путь результата имеет приоритет; в оркестрации соблюдай согласованный координатором `output`.
2. Сохрани основной Markdown по пути из раздела «Артефакт». Сохрани связанные материалы рядом или в предусмотренных для них каталогах. Код и тесты существующего проекта оставь в его структуре, внешнюю доску — в её сервисе; в основном документе запиши реальные пути/ссылки. Не сохраняй результаты в каталог установленного скилла и не перезаписывай материалы другой задачи. При обновлении своего документа сохраняй ID, происхождение и актуальную версию.
3. Проверь фактическую запись и доступность файлов, а также ссылки на приложения. Само упоминание пути не означает сохранения. Недоступные запись или приложения явно назови; не заявляй о сохранении или полной доставке, если они не выполнены. Отсутствие файловых инструментов не мешает выдать полный документ в чат.
4. В ответе пользователю дай краткий **вывод по работе скилла** (что получено, статус/гейт, существенные выводы и ограничения), ссылки на сохранённые файлы и **полный текст основного Markdown-документа прямо в чате**. Краткая сводка, ссылка или ZIP не заменяют полного текста. Дублируй ту же версию, что сохранена, включая таблицы, встроенные диаграммы и JSON-блоки; не сокращай разделы молча. При ограничении длины разбей текст на пронумерованные последовательные части; если среда не позволяет вывести всё, явно укажи недоставленные части и не объявляй дублирование завершённым.
5. Код, изображения, traces, JSON-файлы и стенды передай доступными файлами/папкой/ZIP со ссылками; визуальные материалы покажи в чате, если среда поддерживает просмотр. Бинарные данные и весь исходный код не преобразовывай в текст отчёта. Для внешней доски дай рабочую ссылку и статус доступа.
6. Если работу выполняет субагент, он сохраняет назначенный отчёт и передаёт основной сессии путь, полный Markdown и краткий вывод; при невозможности передачи большого текста основная сессия читает сохранённый файл. **За дублирование в пользовательском чате отвечает основная сессия**: внутренний ответ субагента не считается доставкой пользователю. Изоляция read-set сохраняется; другим ревьюерам отчёт не передавай. В автоматической связке evidence/review выведи manifest, каждый фактически полученный отчёт и synthesis полностью, с именами файлов и общим выводом. Отсутствующие результаты обозначь явно.

Полноту сохранения и доставки сообщай отдельно от оценки продукта и профильного гейта: ошибка записи не доказывает дефект интерфейса. Не создавай отдельный аналитический отчёт о доставке.

## ID и актуальность

Сохраняй предоставленные REQ/RULE/STATE/S/FLOW/UI/TEST-ID. Для новых ID используй устойчивую локальную конвенцию; не перенумеровывай старые ради шаблона. Scenario/test IDs для приложенного runner — непустые ASCII идентификаторы из букв, цифр, _, -, ., :, длиной до 128, начиная с буквы/цифры; тест имеет title `<исходный S-ID> — наблюдаемый результат [<исходный TEST-ID>]`. Parser сравнивает с явным контрактом, а не требует S01. Для несовместимой внешней конвенции создай явную взаимно однозначную таблицу alias → source ID внутри результата, не меняя смысл/источник.

Указывай версию документа и фактическую ревизию кода/evidence. При использовании нескольких источников сверяй их совместимость и раскрывай расхождения. Наличие чужого PASS не подтверждает текущую ревизию.

## Четыре независимых статуса

1. **status** — полнота результата: `complete` (вся заявленная область обработана), `partial` (полезная часть готова, остались ограничения), `blocked` (нет оснований выполнить основную работу). Это не оценка качества продукта.
2. **decision_status** — полномочность существенных решений: `accepted` (подтверждены источником/пользователем), `delegated` (приняты в границах явного делегирования), `proposed`, `unknown`, `N/A`. При смешанном статусе перечисли решения отдельно. Ни status, ни gate не согласовывают решение автоматически.
3. **gate** — готовность результата к заявленному использованию: `PASS`, `LIMITED`, `FAIL`. PASS требует обязательных условий; LIMITED разрешает только явно неблокирующие ограничения; FAIL означает blocker или невыполненное обязательное условие. FAIL из-за непроведённой проверки не означает доказанный дефект продукта. Конкретную строгость задаёт профильный чеклист.
4. **check result** — результат отдельной проверки: `PASS`, `FAIL`, `NOT_CHECKED`, `N/A`. NOT_CHECKED — проверка не выполнена; N/A — доказанная неприменимость с причиной. Частично выполненную проверку разбей на проверенную и непроверенную части.

`draft` — описание черновика, не gate; `approved` — прежнее обозначение согласования, не полноты; старые `PASS with open questions/limitations` трактуй по содержанию: PASS при выполненных обязательствах и необязательных вопросах, LIMITED при неблокирующем ограничении охвата. Старые `DRAFT/NOT_CHECKED` в gate преобразуй в FAIL, если затронуто обязательное условие, иначе LIMITED. Причину и исходный статус сохраняй.

Runtime `captured/blocked`, worker `pending/running/completed/failed/cancelled` и результаты probes `passed/failed/not_checked/not_applicable` — технические состояния инструментов. Они не подменяют четыре поля выше.

## Использование входа с незакрытым гейтом

Не требуй PASS внешнего документа как условия запуска. Используй подтверждённые части в доступной области. Блокирующий вопрос не становится принятым поведением; отметь влияние на собственный результат. Не запускай другие навыки автоматически, кроме явно назначенной evidence/review orchestration.
