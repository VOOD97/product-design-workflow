# Cognitive Walkthrough и проверка контракта

## Подготовка

Определи целевую роль, задачу, стартовые знания, entry point и наблюдаемый успех. Новичок — default lens, а не выдуманная характеристика любой аудитории. Отдельно покажи, если контракт предполагает обученного специалиста. Не читай код, чтобы заранее узнать скрытую последовательность пользователя.

## Прохождение

Пройди primary flow через Playwright обычными действиями, затем применимые P0 alternative/recovery paths. На каждом значимом шаге оцени:

| Линза | Вопрос | На чём строится вывод |
|---|---|---|
| Goal | Понятно ли, какой промежуточный результат нужен сейчас? | Видимая задача, контекст и знания роли |
| Discoverability | Может ли человек заметить допустимое действие? | Screenshot/видимый control, hierarchy и доступность input mode |
| Mapping | Понятна ли связь control с ожидаемым действием? | Label, context, consequences; реальная реакция при click |
| Feedback | Понятно ли, что изменилось и можно ли двигаться дальше? | Processing/result/error, состояние данных и доступность следующего шага |

Записывай yes/risk/no/NOT_CHECKED с наблюдением и check ID. Test-id помогает автоматизации, но не доказывает discoverability; знание DOM selector нельзя приписывать человеку. Автоматическое обнаружение button также не доказывает его визуальную заметность.

Не засчитывай прямой deep link в terminal state как прохождение пути. Используй его лишь для осмотра состояния и явно назови способ достижения. Если Playwright locator не сработал, сначала исключи инструментальную причину; нельзя делать вывод «пользователь не найдёт» по одному неверному selector.

## Product / Flow consistency

Для всех обязательных действий/условий соотнеси источник → предусмотренный путь → реально доступный результат. Проверь:

- entry и разрешённую роль; доступность основного действия;
- branches/guards и значимые states;
- ошибки/partial outcome, сохранение уже успешного и recovery;
- Back/Cancel/refresh только по применимому контракту;
- отсутствие лишних scope additions и утраченных обязательств.

Различай UI запрет, реальную permission гарантию и неизвестный backend контракт. Обнаруженная кнопка — не завершённая операция. Визуально хороший экран с недоступным обязательным результатом имеет product/flow проблему; один cosmetic finding её не описывает.

Одно нарушение, найденное walkthrough, Nielsen и consistency, становится одним finding с несколькими основаниями. В отчёте сохраняются все три coverage tables, но не три копии дефекта.
