# Примеры решений и конфликтов

## Требование и интерфейсное решение

`FACT`: подтверждённое правило BR-04 — retry повторяет только неуспешные элементы.

`proposed`: UI-017 показывает summary и раскрываемый список failures; пользователь пока не выбирал layout.

После явного выбора: `accepted`, источник — сообщение/документ с выбранным решением; сохранить reference именно на выбранный вариант. Сам факт существования макета не подтверждает выбор.

Нельзя заменить partial summary одним toast при реализации стенда и назвать это «упрощением UI» без согласования материального изменения.

## DS gap

Доступный компонент таблицы поддерживает single selection, а подтверждённый сценарий требует multi selection. Сначала проверь существующие варианты и паттерны; опиши конкретный gap. Предложи ограниченное расширение или альтернативу и вынеси material choice. Не меняй общую библиотеку и не создавай конкурирующий table pattern молча.

## Самостоятельный вызов без DS

Для нового локального прототипа пользователь просит экран onboarding, бренд и DS не заданы. Предложи provisional токены внутри стенда: роли background/text/action/error, typography scale, spacing scale, focus style. Запиши scope и статус; покажи результат. Принятое визуальное решение не превращает этот набор автоматически в общую DS организации.

## Недоступный канон

Пользователь просит встроить экран в существующий продукт, но макеты/продукт недоступны. Можно подготовить draft по доступным material constraints, но нельзя утверждать каноническое соответствие. Вопрос — где получить конкретную визуальную опору; не требуй вызова другого скилла.

## Предложение до вопроса

Задан контракт BR-04: повторяются только неуспешные приглашения. В продукте доступна сводка массовой операции с раскрываемыми подробностями. Опора известна, но способ показать ошибки на новом экране пока не принят.

Предложение: «Рекомендую сохранить сводку и раскрываемый список ошибок, как на экране X: это сохраняет общий результат и позволяет исправлять отдельные записи. Компромисс — детали требуют раскрытия. Альтернатива — сразу показать таблицу всех результатов; она удобнее для последовательного разбора, но плотнее. Для текущего сценария я бы выбрал сводку. Оставляем этот принцип или важнее сразу видеть все ошибки?»

Название экрана X в реальной задаче замени проверенным источником; пример не доказывает существование такого экрана. Не спрашивай заново о семантике retry, если она уже принята. До решения UI остаётся proposed. После ответа обнови только выбранную композицию, сохрани BR-04 и остальные решения. Если пользователь делегировал композицию, выбери в этих границах без вопроса.

Если продуктовый смысл частичного успеха неизвестен, сначала обозначь этот пробел: визуальная рекомендация не может подменить бизнес-правило. При просьбе «сделай полный экран без вопросов» продолжай определённые части, фиксируя неизвестное и статус draft.

## Явное делегирование

Если пользователь разрешил выбрать композицию самостоятельно, accepted decision может иметь основание «принято в пределах делегирования» с точной областью. Не спрашивать повторно о той же области; делегирование layout не разрешает менять права, механику или scope.
