# Сбор evidence и запуск независимого ревью

Сними воспроизводимые доказательства текущего прототипа и, после готовности evidence, автоматически выполни назначенный параллельный review и затем синтез в основной сессии. Это явно заданная связка, а не требование пройти какие-либо предыдущие процессы.

Прочитай `references/artifact-contract.md`: применяй единые правила источников, ID, статусов документа, решения, гейта и отдельных проверок, а также выбора папки, сохранения и полного дублирования результата в чате. Это правила формата, а не зависимость от других навыков.

## Вход и ресурсы

Достаточны проверяемый прототип/URL, задача, тестовый доступ и наблюдаемый контракт. При наличии используй ui-spec.md, solution.md со сценариями, flow.md, requirements.md и нейтральный test contract. Файлы необязательны; если их нет, составь scope и нейтральную матрицу из текущего запроса, подтверждённого поведения и делегирования. Не выдумывай успешные проверки и принятые решения.

Вначале прочитай `references/playwright-setup.md` и `references/collector-contract.md`; для запуска reviewers — `references/review-orchestration.md`. Используй `assets/capture-config.example.json` как адаптируемую форму, а `assets/manifest-template.md` как единственный текстовый отчёт. Перед завершением обязательно пройди `references/evidence-ready-checklist.md`.

Если доступен `solution.md`, используй его раздел «Сценарии» вместе с правилами и состояниями, сохраняя ID. Отдельный файл сценариев не ожидается. Другие предоставленные документы допустимы как внешние источники: проверь версию, полномочность и область; конфликт с текущим контрактом зафиксируй, не разрешай по одному имени файла. При отсутствии документов восстанови только нужный текущей задаче контракт внутри основного результата.

До конфигурации сбора прочитай `references/test-contract-handoff.md`. Извлеки единственный prototype-test-contract в технический test-contract.json скриптом test_contract.py; если такого источника нет, составь этот нейтральный контракт по текущему запросу и реальным tests/fixtures. Создай capture-config через build-config с фактическими wait/actions, затем выполни verify. Укажи testContract в конфигурации и sourceFiles; сокращать ожидаемые критерии нельзя. Read-set получает исходный контракт, а не обратную реконструкцию из конфигурации.

## 1. Определи предмет и версию

Установи фактическую обслуживаемую revision, URL/порт, mock reset/seed, роли, screens×states×viewports, primary/P0 alternative flows и функциональную матрицу. P0 — обязательный scope, не finding severity. Проверь связь запущенного сервера с исходниками и revision; строка версии в конфиге сама по себе этого не доказывает.

Укажи явные sourceFiles: относящиеся к задаче исходники, тесты, canonical docs/brief. Не сканируй весь проект и не включай секреты/чужие данные. Хеши до/после снимут изменение файлов; несогласованный live сервер всё ещё требует проверки оператора. Не запускай сбор на настоящих клиентских данных и не совершай изменяющие действия в live продукте.

Если область/прототип неизвестны, задай конкретные вопросы; при невозможности диалога верни полный доступный manifest с FAIL и условиями продолжения. Не требуй другого скилла.

## 2. Подготовь воспроизводимый прогон

Проверь Playwright, браузерные binaries, @axe-core/playwright, Node и Python для планировщика. Существующую проектную настройку переиспользуй. Установка пакета без Chromium не достаточна. Если требуется Linux system dependencies, перечисли реальные ошибки/условия настройки, не обходя ограничения среды.

Из matrix/нейтрального блока сформируй capture-config: named viewports, отдельная цель для UI×state×viewport, безопасный путь, действия и маркер ожидаемого состояния. Состояния должны быть воспроизводимы через fixtures, seed/query или подготовленный тестовый context. Не используй случайные данные и fixed sleeps вместо ожидаемого состояния. Аутентификацию адаптируй отдельно; secret storage не доставляй вместе с evidence.

Реальный тест имеет title `S01 — observable result [TEST-001]`. Один заявленный S/TEST соответствует реально исполняемому meaningful test. Пользовательский observable_result проверяется assertions, а не просто существованием теста или кнопки. Исходные совместимые S/TEST-ID сохраняй: parser сравнивает их с явными cases, включая ID с дефисом/двоеточием. Для несовместимого синтаксиса используй документированную взаимно однозначную alias-таблицу, не меняя источник и смысл.

## 3. Сними evidence

Проверь конфиг dry-run, затем выполни один воспроизводимый command в новый run-directory:

```bash
node <skill-dir>/scripts/capture-evidence.cjs \
  --config <task-dir>/capture-config.json --project <project-dir> \
  --out <task-dir>/evidence/<run-id>
```

Сборщик сохраняет реальные screenshots, traces, functional-results, axe-report, keyboard trace, console log и capture-result с хэшами. Он не запускает сервер, не генерирует продуктовые тесты и не является полностью универсальным recorder. Подготовку project selectors/dataset сделай до прогона. Для иной среды можно использовать проектный runner, но соответствующие проверяемые данные, provenance и gates обязательны.

Axe violations — результат scan для оценки reviewer, не признак неуспешного сбора. Keyboard trace содержит реальные клавиши и фокус, но доступные role/name из DOM могут быть приближёнными. Ни axe, ни лог не доказывают полноценную доступность. Автоматический сбор не заменяет просмотра screenshot и семантики focus.

Первый screenshot не объявляй принятой visual baseline. Не принимай обновление эталонов и не правь продукт. P0 failed/skipped/flaky/missing либо недоступный browser/scan/trace — Evidence Ready FAIL; с такими входами reviewers не запускаются. Верни доказательства неуспеха и блокеры. Исправления по этому навыку не выполняются.

## 4. Проверь готовность и зафиксируй manifest

Пройди чеклист, сверь ожидаемые и снятые tuple UI×state×viewport, реальные P0 результаты, source/evidence hashes, версии и ограничения. Открой доступные screenshots и убедись, что показано нужное состояние, а не login/ошибка/blank. Без просмотра обозначь ограничение качества; неверное состояние блокирует запуск.

Заполни `manifest.md` в папке run. Его ссылки, команды и версия должны быть точными. В техническом capture-result статус captured означает сбор, а не независимую оценку качества. Не допускай PASS при неполной обязательной матрице. До ревью зафиксируй Evidence Ready и capture_sha256.

## 5. Автоматически запусти пять reviewers

Когда Evidence Ready PASS, продолжи без отдельного предложения «могу начать ревью». В основной сессии прочитай `references/review-orchestration.md`, подготовь review-run и одновременно запусти независимые workers:

- UX Critic — `ux-critic` с `ux-review`;
- Visual Critic — `visual-critic` с `visual-review`;
- Accessibility Reviewer — `accessibility-reviewer` с `accessibility-review`;
- Content Reviewer — `content-reviewer` с `content-review`;
- Design ↔ Code Parity Reviewer — `design-code-parity-reviewer` с `design-code-parity-review`.

У каждого свой чистый контекст/read-set и output. Не передавай авторские build-notes/рассуждения, чужие выводы или ожидаемый диагноз. При доступном прототипе reviewers самостоятельно проверяют существенные гипотезы через Playwright; им передаются URL, test fixtures и reviewer-owned evidence directory. Параллельный browser доступ — отдельные contexts и независимые backend datasets/namespaces, не общая изменяемая page или общий reset. Не запускай конкурирующие workers последовательно и не представляй работу одной роли как пять независимых проверок. Лимит среды или недоступность agents запиши BLOCKED orchestration, сохрани evidence; не обходи permissions.

## 6. Дождись барьера и подключи синтезатор

Дождись terminal status всех пяти workers, проверь сохранённые отчёты и совпадение provenance. Автоматически загрузи и выполни скилл `review-synthesis` в основной сессии после барьера. Он получает reports и evidence, убирает дубли, фиксирует противоречия, группирует findings и сохраняет synthesis.md; отдельный субагент-синтезатор не требуется, продукт не исправляется.

Если worker упал/отменён, зафиксируй failed/missing и после всех terminal statuses сформируй ограниченный synthesis с FAIL/неполным coverage. Если скилл синтеза недоступен, сохрани отчёты и укажи блокировку; не выдумывай его результат и не выдавай полный Reviews Ready. Структурный verify_reports не заменяет проверку sources/evidence и смысловой синтез.

Не заканчивай успешный автоматический вызов на одном evidence pack: выдай результаты только после synthesis. Во время ожидания сообщай прогресс; незавершённое не называй завершённым. Не запускай fixes, новый baseline, повторное ревью, commit/deploy автоматически.

## Перед завершением

Повтори `references/evidence-ready-checklist.md` для неизменной revision, а затем проверь завершение reviewer outputs и результат основного синтеза по `references/review-orchestration.md`. В manifest отдельно запиши Evidence Ready и Reviews Ready — это разные результаты. Findings Critical/High не делают evidence неготовым, но остаются проблемами продукта.

## Артефакт

Выбери и при необходимости создай `<task-dir>` по `references/artifact-contract.md`. Сохрани основной документ в `<task-dir>/evidence/<run-id>/manifest.md`. После сохранения продублируй полный Markdown в пользовательском чате вместе с кратким выводом и ссылками на файлы; при работе через субагента доставку выполняет основная сессия. При недоступной записи выдай полный текст и явно сообщи, что файл не сохранён.

Основной результат этого навыка — **один `manifest.md` в формате Markdown** с областью, фактической revision, командой воспроизведения, матрицей evidence, хэшами/ссылками, гейтом и ограничениями. Raw JSON, images, traces и logs — evidence assets того же отчёта.

По завершении автоматического review дополнительно выдай назначенные результаты workers: `reviews/<run-id>/ux.md`, `visual.md`, `accessibility.md`, `content.md`, `parity.md`, `synthesis.md`. Это явно заданные результаты отдельных навыков, а не второй аналитический отчёт evidence-capture. Основная сессия полностью дублирует в пользовательском чате `manifest.md`, каждый полученный отчёт ревью и `synthesis.md` с общим выводом; ссылка на комплект не заменяет эти тексты. Raw evidence сохрани в `<task-dir>/evidence/<run-id>/`, отчёты — в `<task-dir>/reviews/<run-id>/`. Доставь весь комплект ZIP с относительными ссылками или доступными путями; localhost другого компьютера не является передаваемым артефактом. При блокировке выдай сделанное и конкретное условие продолжения.
