# Product Design Skills & Agents

Набор из **14 скиллов и 5 агентов** для продуктового дизайнера: от постановки задачи и моделирования поведения до интерфейса, прототипа в коде и независимого ревью.

Скиллы можно использовать последовательно в одной продуктовой задаче или выбирать по отдельности. Если прототип уже готов, можно сразу запустить нужное ревью. Если нужен только user flow, не требуется предварительно создавать требования, исследование и модель решения другими скиллами.

Инструкции и поля `description` скиллов и агентов написаны на русском; технические имена и ключи метаданных сохранены на английском.

## С чего начать

1. При необходимости сверьте свою задачу с [таблицей скиллов](#какой-скилл-выбрать). Знать имя скилла для запроса не требуется.
2. [Установите](#установка) нужную папку скилла целиком или весь пакет.
3. Опишите задачу обычными словами и передайте имеющиеся материалы. Агент выбирает подходящий доступный скилл по смыслу запроса и контексту работы, опираясь на `description`; имя можно указать для явного выбора. Примеры — в разделе [«Примеры запросов»](#примеры-запросов).
4. Получите результат и проверьте его статус: что сделано, какие решения приняты и что осталось неизвестным.

**Особенность текущего пакета:** `evidence-capture` объединяет сбор evidence и последующий запуск всех пяти ревьюеров с синтезом. Для отдельного UX-, визуального или другого ревью опишите нужную область проверки: ей соответствует профильный review-скилл. Запрос только на скриншот, запись теста или сбор evidence без последующих ревью не должен автоматически запускать полную цепочку.

## Как устроен репозиторий

В корне репозитория находятся этот `README.md` и три папки: `skills/`, `agents/` и `tests/`. Инструкции, шаблоны и методические справочники хранятся внутри соответствующих скиллов.

| Путь | Что находится внутри |
|---|---|
| [`skills/`](skills/) | 14 папок с самостоятельными инструкциями и ресурсами |
| `skills/<name>/SKILL.md` | Назначение, входы, процедура, границы ответственности и результат скилла |
| `skills/<name>/references/` | Методические справочники, правила и чеклисты готовности |
| `skills/<name>/assets/` | Шаблоны документов, конфигураций и примеры |
| `skills/<name>/scripts/` | Вспомогательные скрипты там, где они нужны |
| [`agents/`](agents/) | Определения пяти независимых ревьюеров |
| [`tests/`](tests/) | Автоматические проверки и учебные примеры прогонов |

**Скилл** описывает, как выполнять работу. **Агент** задаёт отдельную роль и условия её выполнения. Например, `ux-critic` использует методику из `ux-review`.

У каждого скилла есть локальная копия общего `references/artifact-contract.md`. Это намеренное дублирование: папку скилла можно передать отдельно, сохранив необходимые правила. Не копируйте только `SKILL.md` — ему нужны связанные ресурсы.

## Какой скилл выбрать

| Задача | Скилл | Основной результат |
|---|---|---|
| Разобрать готовый PRD, тикет или набор требований | [`requirements-normalization`](skills/requirements-normalization/SKILL.md) | `requirements.md`: требования, критерии приёмки, конфликты и вопросы |
| Превратить идею или пожелание в постановку проблемы | [`problem-framing`](skills/problem-framing/SKILL.md) | `requirements.md`: проблема, цели, гипотезы и первые требования |
| Изучить конкурентов, аналоги и способы решения похожих задач | [`competitive-research`](skills/competitive-research/SKILL.md) | `competitive-research.md`; Research Stand — по выбранному формату |
| Определить механизм решения, правила, состояния и сценарии | [`solution-scenario-modeling`](skills/solution-scenario-modeling/SKILL.md) | `solution.md`, включая сценарии |
| Спроектировать основной путь, развилки и восстановление | [`flow-design`](skills/flow-design/SKILL.md) | `flow.md` с Mermaid; отдельная визуализация — по выбранному формату |
| Спроектировать экраны, состояния и взаимодействия | [`ui-interaction-design`](skills/ui-interaction-design/SKILL.md) | `ui-spec.md` и Design Stand с отрисованными экранами и состояниями |
| Собрать интерактивный прототип в коде | [`prototype-build`](skills/prototype-build/SKILL.md) | Код, тесты и `prototype-build.md` |
| Собрать доказательства работы прототипа и провести полный цикл ревью | [`evidence-capture`](skills/evidence-capture/SKILL.md) | Evidence pack с `manifest.md`, пять отчётов и `synthesis.md` при успешном завершении цепочки |
| Проверить удобство сценария и восстановление после ошибок | [`ux-review`](skills/ux-review/SKILL.md) | `ux.md` |
| Проверить визуальную иерархию, состояния и согласованность интерфейса | [`visual-review`](skills/visual-review/SKILL.md) | `visual.md` |
| Проверить клавиатуру, фокус, формы и другие аспекты доступности | [`accessibility-review`](skills/accessibility-review/SKILL.md) | `accessibility.md` |
| Проверить тексты, терминологию, сообщения и форматы данных | [`content-review`](skills/content-review/SKILL.md) | `content.md` |
| Сверить принятые решения с кодом, поведением и тестами | [`design-code-parity-review`](skills/design-code-parity-review/SKILL.md) | `parity.md` |
| Свести отчёты, убрать дубли и разобрать противоречия | [`review-synthesis`](skills/review-synthesis/SKILL.md) | `synthesis.md` |

`requirements-normalization` и `problem-framing` — два входа в один этап. Выбирайте первый, если требования уже есть, и второй, если постановку ещё нужно сформировать. Запускать оба подряд по умолчанию не требуется.

Соответствие агентов и скиллов:

| Агент | Используемый скилл |
|---|---|
| [`ux-critic`](agents/ux-critic.md) | `ux-review` |
| [`visual-critic`](agents/visual-critic.md) | `visual-review` |
| [`accessibility-reviewer`](agents/accessibility-reviewer.md) | `accessibility-review` |
| [`content-reviewer`](agents/content-reviewer.md) | `content-review` |
| [`design-code-parity-reviewer`](agents/design-code-parity-reviewer.md) | `design-code-parity-review` |

Агенты ссылаются на скиллы через поле `skills:` и наследуют модель. Их инструкции ограничивают чтение и запись, но сами по себе не создают техническую песочницу. Реальные права задаёт среда выполнения.

## Примеры запросов

Основные примеры ниже не требуют имени скилла: агент должен распознать задачу по смыслу, в том числе когда она возникает как этап более длинной сессии. После заголовка указан ожидаемый скилл для проверки выбора. Замените пути, ссылки и описание задачи своими данными.

Для явного выбора можно дополнительно написать, например, «Используй flow-design». Имя — один из допустимых способов обращения, а не обязательный триггер. Автоматическое подключение зависит также от установки, доступности скилла и настроек клиента; одни ключевые слова не гарантируют запуск.

### Есть только идея

Ожидаемый скилл: `problem-framing`.

```text
Хочу помочь менеджерам обрабатывать массовые приглашения пользователей.
Помоги сформулировать проблему и первые требования.
Сейчас известны такие проблемы: …
Сначала используй доступные вводные, затем задай только существенные вопросы.
Сохрани результат в work/bulk-invitations/.
```

### Нужен только flow

Ожидаемый скилл: `flow-design`.

```text
Построй пользовательский путь отмены заказа: основной сценарий,
развилки и восстановление. Правила и ограничения: …
Готового solution.md нет. Формат результата — document:
flow.md со встроенными Mermaid-диаграммами, без отдельной визуальной поверхности.
```

### Нужно исследование с визуальным представлением

Ожидаемый скилл: `competitive-research`.

```text
Изучи, как другие продукты показывают
частичный успех массовой операции и позволяют повторить неудачные действия.
Не ограничивайся прямыми конкурентами: изучи аналогичные продукты,
смежные рынки и неочевидные паттерны по сходству задачи.
Контекст нашей задачи: … Формат результата — document+stand.
```

### Уже есть прототип, нужно только UX-ревью

Ожидаемый скилл: `ux-review`.

```text
Проверь удобство тестового прототипа по адресу <URL>.
Пользователь и его задача: … Основной сценарий: …
Тестовая роль, данные и способ сброса: …
Проверь основной путь и восстановление после ошибки.
Верни замечания, удачные решения и границы проверки.
```

### Нужны сбор evidence и все пять ревью

Ожидаемый скилл: `evidence-capture`, затем профильные ревью и `review-synthesis`.

```text
Собери воспроизводимые доказательства работы прототипа <URL>
в проекте <path> и проведи полный цикл независимого ревью.
Контракт задачи и критерии проверки: …
Команда запуска, тесты, fixtures и изоляция данных: …
После готовности evidence выполни пять независимых ревью и синтез.
```

### Уже есть отчёты

Ожидаемый скилл: `review-synthesis`.

```text
Подготовь единый итог по приложенным отчётам независимых ревью
и расставь приоритеты замечаний.
Область проверки и версия прототипа: …
Объедини дубли с сохранением исходных ID, разбери противоречия
и отдели подтверждённые проблемы от того, что ещё нужно проверить.
```

## Обсуждение решений и продолжение после ревью

`solution-scenario-modeling` и `ui-interaction-design` начинают существенный выбор с доступной опоры, обоснованного предложения и рекомендации. В диалоге обычно обсуждается один важный выбор за ответ; известные решения не согласуются заново, а явное делегирование позволяет действовать самостоятельно. Это формат общения: полный запрошенный результат и работа над независимыми частями сохраняются.

`review-synthesis` различает причину следующего действия: нужно уточнить продуктовое правило, принять визуальное решение, реализовать уже принятое обязательство, устранить визуальное расхождение или сначала получить недостающее свидетельство. В итоговом отчёте есть полная маршрутизация и один ближайший рекомендуемый шаг с ответственным, обязательностью и критерием проверки. Рекомендация не запускает исправления автоматически и не означает принятия продукта.

## Работа над большой продуктовой задачей

Возможная последовательность:

1. **Требования:** `requirements-normalization` или `problem-framing`.
2. **Исследование:** `competitive-research`, если нужно изучить аналоги и паттерны.
3. **Поведение продукта:** `solution-scenario-modeling`.
4. **Пути пользователя:** `flow-design`.
5. **Интерфейс:** `ui-interaction-design`.
6. **Работающий прототип:** `prototype-build`.
7. **Evidence и независимое ревью:** `evidence-capture` с последующим синтезом.

Это маршрут, который пользователь или основная сессия собирает под задачу. Обычный скилл не запускает всю цепочку автоматически. Уже имеющиеся решения и материалы позволяют начать с нужного этапа или пропустить ненужный.

Передавайте следующему этапу актуальные документы, принятые решения и ограничения. Существенные вопросы остаются видимыми; явно делегированные решения агент может принимать в заданных границах.

Полный исходный дизайн-воркфлоу шире этого пакета. Отдельные процессы Context / Intake, Tech Feasibility, Fix & Validation и Final Handoff здесь не оформлены как самостоятельные скиллы. Управление всей задачей и этими переходами остаётся за основной сессией и дизайнером.

## Формат Flow и Research

`competitive-research` по умолчанию ищет решения за пределами прямых конкурентов: рассматривает аналогичные продукты, смежные рынки и неожиданные паттерны с начала исследования. Широта поиска определяется сходством задачи и переносимостью принципов. Ограничение только конкурентами требует явно узкого запроса или конкретного обоснования; обязательных находок в каждой категории нет.

В начале работы скилл фиксирует формат результата и основание выбора.

| Скилл | Формат | Что выдаётся |
|---|---|---|
| `flow-design` | `document` | `flow.md` со встроенными Mermaid-диаграммами |
| `flow-design` | `document+local` | Документ и отдельное локальное представление модели |
| `flow-design` | `document+figjam` | Документ и сохранённая, проверенная FigJam board |
| `competitive-research` | `document` | `competitive-research.md` и относящееся к выводам evidence |
| `competitive-research` | `document+stand` | Документ и локальный Research Stand |

Явный запрос и ранее согласованный формат имеют приоритет. Если формат не задан, используется `document` без дополнительного согласования. Отсутствие не выбранного представления не снижает готовность: оно получает `not-required`, связанные проверки — `N/A`.

Если доска или стенд входят в согласованный результат, недоступность их создания или проверки фиксируется как ограничение. Скилл не должен молча сокращать результат ради `PASS`.

Это правило относится к Flow и Research. `ui-interaction-design` по-прежнему предусматривает `ui-spec.md` вместе с Design Stand.

## Как работает независимое ревью

Каждый review-скилл можно вызвать отдельно с текущей задачей и доступными материалами. Наличие полного комплекта документов и предварительный запуск `evidence-capture` для такого вызова не обязательны. Если интерактивный доступ отсутствует, выводы ограничиваются предоставленными материалами; непроверенное обозначается явно.

Полная связка в `evidence-capture` устроена так:

1. Подготовить воспроизводимый прогон и собрать screenshots, traces, функциональные результаты, axe-отчёт, клавиатурный след и логи для конкретной версии.
2. Проверить Evidence Ready. Неуспешный, пропущенный, нестабильный или отсутствующий P0 functional check блокирует автоматический запуск ревьюеров.
3. Запустить пять ревьюеров параллельно, выдав каждому свой набор входов, каталог результата и изолированные тестовые данные.
4. Дождаться завершения всех ролей и проверить происхождение отчётов.
5. Выполнить `review-synthesis` в основной сессии и передать итоговый комплект. Отдельного агента-синтезатора нет.

Независимые ревьюеры не получают авторскую самооценку реализации и выводы друг друга. Они могут самостоятельно проверять существенные гипотезы в тестовом браузере. Продуктовый код читает только Parity Reviewer — для сверки с принятыми решениями, а не общего инженерного code review.

В текущей автоматической связке обязательны все пять ролей и возможность их параллельного запуска. При недоступности нужных агентов или слотов оркестрация отмечается заблокированной; собранные материалы сохраняются. После синтеза исправления, принятие визуальных эталонов и deployment автоматически не запускаются.

Подробности: [оркестрация ревью](skills/evidence-capture/references/review-orchestration.md), [общий протокол](skills/ux-review/references/review-protocol.md).

## Результаты и статусы

Каждый обычный скилл создаёт один основной Markdown-документ. Код, изображения, JSON, traces и стенды — связанные материалы результата. Автоматическая связка evidence/review дополнительно выдаёт отчёты всех назначенных ролей и синтез.

Сценарии хранятся внутри `solution.md`. Матрица тестов, нейтральный блок `prototype-test-contract` и авторский журнал — внутри `prototype-build.md`. Отдельные обязательные `scenarios.md`, `test-matrix.md` и `build-notes.md` не ожидаются. Внешние документы с такими именами можно использовать как источники с проверкой актуальности.

Каждый скилл самостоятельно выбирает и создаёт папку результатов: указанная пользователем → уже установленная папка этой задачи → `work/<task-slug>/` от корня рабочего проекта (без проекта — от текущей рабочей папки). Для этого не нужно предварительно запускать `problem-framing` или `requirements-normalization`. Точный назначенный путь имеет приоритет; субагенты используют `output` координатора. Существующие ID сохраняются, источники и версии фиксируются. Папки установленных скиллов содержат методику, а не результаты конкретной продуктовой задачи.

Основные документы сохраняются в папку задачи; самостоятельные ревью и синтез — в `reviews/`, автоматический запуск — в `reviews/<run-id>/`, manifest и raw evidence — в `evidence/<run-id>/`. Код/тесты остаются в структуре рабочего проекта, внешние доски — в своём сервисе; документ содержит реальные ссылки.

**Результат выдаётся и файлом, и полностью в чате.** Пользователь получает краткий вывод по работе скилла, ссылки на сохранённые материалы и полный текст основного Markdown-документа той же версии. Ссылка, ZIP или краткая сводка не заменяют текст. Большой документ делится на последовательные части; невозможность полного вывода сообщается явно. Код, изображения, traces и стенды передаются файлами/ссылками, с просмотром визуальных материалов при поддержке среды. Если запись недоступна, скилл всё равно выдаёт полный Markdown и прямо сообщает, что файл не сохранён.

За вывод результатов субагентов в пользовательском чате отвечает основная сессия. В автоматической связке evidence/review она дублирует manifest, все полученные отчёты и synthesis с общим выводом; внутренние ответы workers не считаются доставкой пользователю. Полные правила находятся в локальном `references/artifact-contract.md` каждого скилла.

| Поле | На какой вопрос отвечает | Значения |
|---|---|---|
| `status` | Насколько выполнена заявленная работа? | `complete`, `partial`, `blocked` |
| `decision_status` | Приняты ли существенные решения и на каком основании? | `accepted`, `delegated`, `proposed`, `unknown`, `N/A` |
| `gate` | Готов ли результат к заявленному использованию? | `PASS`, `LIMITED`, `FAIL` |
| Результат отдельной проверки | Что фактически проверено? | `PASS`, `FAIL`, `NOT_CHECKED`, `N/A` |

`LIMITED` означает явно названное неблокирующее ограничение; `FAIL` — блокер или невыполненное обязательное условие. `NOT_CHECKED` означает отсутствие проверки, `N/A` — обоснованную неприменимость.

Готовность отчёта и качество продукта — разные оценки. Полное ревью может получить `PASS` и одновременно содержать серьёзные проблемы продукта. `PASS` также не означает автоматического согласования решений, подтверждения пользовательской ценности или готовности к production.

## Инструменты и подготовка окружения

Устанавливайте только то, что требуется выбранной задаче.

| Работа | Что потребуется |
|---|---|
| Анализ требований, моделирование решения, текстовый flow | Доступ к инструкциям и материалам; файловые инструменты для сохранения результата |
| Актуальное онлайн-исследование | Доступ к источникам через разрешённые инструменты; без него возможен анализ предоставленных материалов с указанием ограничений |
| Сборка Research Stand | Python 3 для приложенного сборщика и браузер для проверки результата |
| FigJam | Совместимая MCP-интеграция с подтверждённой записью, авторизация и доступ к целевой доске |
| Design Stand и прототип | Среда запуска, стек и компоненты конкретного проекта; браузер для проверки |
| Evidence collector | Node.js 20+, Playwright, браузерные binaries и `@axe-core/playwright` |
| Подготовка контракта и проверка review-пакета | Python 3.9+ |
| Полный параллельный review | Поддержка независимых агентов и изолированные браузерные контексты и тестовые данные |

Collector не запускает сервер и не создаёт продуктовые тесты автоматически. До сбора нужны реальные URL, fixtures, selectors нужных состояний, meaningful assertions и тестовый доступ. Примеры конфигураций в `assets/` — формы для адаптации, а не готовый тестовый набор для любого продукта.

Раздельные BrowserContexts не изолируют общую базу данных. Для параллельных изменяющих действий нужны независимые datasets/namespaces или mocks. Работа ведётся на тестовых данных; секреты и auth state не включаются в передаваемый комплект.
